## Architecture Overview

On The Money is a self-hosted finance tracker made of three pieces: a React frontend, a Spring Boot backend, and an optional C++ Monte Carlo engine. PostgreSQL holds all user data, and FinnHub supplies live market data.

```text
┌────────────────────────────────────────────┐
│ REACT 19  frontend (web/)                  │
│ net worth charting                         │
│ accounts · transactions · stocks           │
│ credit score · MC projection UI            │
│ PWA · Vercel · onthemoney.site             │
└──────────────────────┬─────────────────────┘
                       │   HTTPS · REST
                       │
┌──────────────────────┯─────────────────────┐     ┌────────────────────┐
│ SPRING BOOT  backend (backend/)            │     │ FINNHUB API        │
│ REST controllers · services · JPA          │     │ external service   │
│ BCrypt · session tokens · auth             │     │ quotes · symbols   │
│ FinnHub client · MC engine client          │────▶│ indices · candles  │
│ Plaid client (link · sync)                 │──┐  │ stock data API     │
│ Render · Docker                            │  │  └────────────────────┘
└──────────┬───────────────────────┬─────────┘  │  ┌────────────────────┐
           │                       │            └─▶│ PLAID              │
           │                       │               │ bank linking       │
           │                       │               │ accounts · txns    │
           │                       │               │ synced balances    │
           │                       │               │ encrypted at rest  │
           │                       │               └────────────────────┘
┌──────────┯─────────┐  ┌──────────┯─────────┐
│ C++17 ENGINE       │  │ POSTGRESQL (Vercel) │
│ Monte Carlo        │  │ users · sessions   │
│ 10,000+ sim paths  │  │ accounts · txns    │
│ only used by       │  │ net worth history  │
│ POST /api/project  │  │ credit · watchlist │
│ OS pipes · JSON    │  │ Spring Data JPA    │
└────────────────────┘  └────────────────────┘
```

The frontend is a React single-page app deployed to Vercel; everything it shows arrives as JSON over HTTPS from the Spring Boot API. That API owns the data model, user auth, and the two external integrations — Plaid for banking data and FinnHub for market data. The Monte Carlo engine is the one deliberate outlier: it stays a separate C++ process, buildable and testable on its own, and streams projection results back to Spring Boot over OS pipes.

## Data Model

PostgreSQL stores everything through Spring Data JPA. The model is 8 JPA entities in `backend/src/main/java/com/onthemoney/models/`, with the schema auto-generated by Hibernate (`ddl-auto=update`). Two sources feed the data — Plaid for the ledger and FinnHub for market data — and every row is scoped to a user through a `user_id` foreign key.

```text
users ─┬─ sessions          (one session token per login)
       ├─ plaid_items       (each bank connection, "Item")
       ├─ accounts          (each bank account)
       ├─ transactions      (each transaction)
       ├─ net_worth_history (daily net-worth snapshots)
       ├─ credit_scores     (user-entered credit score)
       └─ watchlist         (stock symbols)
```

- **users** (`UserEntity`) — id, unique email, password (hashed via `setPasswordHash`), displayName, createdAt.
- **sessions** (`SessionEntity`) — the auth mechanism: a random UUID token per login, expiring 30 days out (`SessionEntity.java:35`). No JWT — the frontend sends this token and the `AuthInterceptor` resolves it to a user.
- **plaid_items** (`PlaidItemEntity`) — one row per linked bank: `plaid_item_id` (unique), institution id/name, `status` (`CONNECTED`, `LOGIN_REQUIRED`, `PENDING_EXPIRATION`, `ERROR`, `DISCONNECTED`), a cursor for incremental `/transactions/sync`, `last_sync_at`, and the `access_token` encrypted at rest — marked `@JsonIgnore` so it's never serialized to the frontend.
- **accounts** (`AccountEntity`) — name, balance (always `BigDecimal(19,2)`), and `accType` (`CHECKING | SAVINGS | CREDIT_CARD | LOAN | INVESTMENT`), plus `plaid_account_id`/`plaid_item_id` traces back to Plaid. Plaid's balance is authoritative.
- **transactions** (`TransactionEntity`) — amounts are always positive (`@Positive`); direction lives in `type` (`DEPOSIT | WITHDRAW | TRANSFER`) and `fromAccountId`/`toAccountId`. A unique `plaid_transaction_id` makes imports idempotent — the same Plaid transaction updates rather than duplicates. Webhook-synced transactions are read-only history; they never adjust balances.
- **net_worth_history** (`NetWorthHistoryEntity`) — a daily date + net-worth snapshot per user, recorded each time the Dashboard loads; this feeds the area chart.
- **credit_scores** (`CreditScoreEntity`) — user-entered score (300–850) and date.
- **watchlist** (`WatchlistEntity`) — symbol + addedDate, with a unique constraint on `(user_id, symbol)` so a ticker can't be added twice.

Two quirks worth noting:

- No `@OneToMany` collections — every child holds a `user_id` FK, and relationships are joined by explicit ids (e.g. transactions reference `fromAccountId`/`toAccountId` as plain `Long`s, not FKs).
- Money is always `BigDecimal(19,2)`; floating point is never used for balances.

Because the app is self-hosted, the whole store stays private: Plaid and FinnHub only ever see the API calls they're asked to handle, never the ledger itself.

## Plaid Integration

Plaid is a service that lets users link their bank accounts to the app and gives you programmatic access to that data — `/accounts/balance/get` for balances, `/transactions/get` for history, plus webhooks that fire when something changes. A **Plaid Item** represents one bank connection: effectively a login at a financial institution, identified by an `item_id`.

### Linking a bank

The link flow is a token handshake between the frontend, your backend, and Plaid:

1. **Request a link token.** The client calls `POST /api/plaid/link_token`; the backend calls Plaid's `/link/token/create` with your client name, the user's id, the transactions product, 730 days of history, and the webhook URL, then returns a short-lived `link_token`.
2. **Open Link.** The client uses that token to launch the Plaid Link modal. When the user finishes, Link hands the client a single-use `public_token`.
3. **Exchange it server-side.** The frontend forwards the `public_token` to the backend, which presents it to `/item/public_token/exchange` along with the `client_secret` — which never leaves the server. Plaid trades the token in for a permanent `access_token` and an `item_id`, which the backend keeps for all future product requests.

Doing the swap server-side keeps the keys to your users' financial data out of the browser entirely. The only thing that travels across the wire to the client is the `public_token`, spent the moment it's exchanged.

### Storing the token securely

The `access_token` is a permanent credential, so it's never persisted in plain text. Before storing, the backend encrypts it with AES-256-GCM using Spring Security's `AesBytesEncryptor` (built on `javax.crypto`), then Base64-encodes the ciphertext. The `item_id` and institution metadata aren't sensitive, so they stay in plaintext. Decryption happens only server-side, right before a Plaid call:

```java
public PlaidCrypto(@Value("${application.secret}") String secret) {
  this.encryptor =
      new AesBytesEncryptor(
          secret, secret + "-salt",
          KeyGenerators.secureRandom(IV_LENGTH),
          CipherAlgorithm.GCM
      );
}

public String encrypt(String plaintext) {
  byte[] enc = encryptor.encrypt(plaintext.getBytes(StandardCharsets.UTF_8));
  return Base64.getEncoder().encodeToString(enc);
}

public String decrypt(String encoded) {
  byte[] raw = encryptor.decrypt(Base64.getDecoder().decode(encoded));
  return new String(raw, StandardCharsets.UTF_8);
}
```

### Keeping data current

Two endpoints keep an Item in sync, both called with the stored `access_token`: `/accounts/balance/get` for balances and `/transactions/get` for new transactions. Balances land directly in `AccountEntity.balance`, since the bank's number is the source of truth. Transactions are persisted as read-only history mapped to `DEPOSIT`/`WITHDRAW`, so a sync can never double-count.

The trick is knowing *when* to run this. Rather than polling every account on a schedule, Plaid sends a webhook the moment a transaction posts or a balance changes, and the backend syncs that Item in response. No calls are made unless there's genuinely something new to fetch — which avoids wasted requests and rate limits.

## FinnHub API

FinnHub is a free stock-data API that powers the stocks tab. The app uses the `/quote` endpoint for a stock's current price and the `/candle` endpoint for historical price data. It was chosen because it's free and easy to use, and it gives a finance tracker a lightweight market-data touch without turning the app into a trading platform.

## User Authentication

Authentication is Spring Security with BCrypt password hashing and UUID token sessions — deliberately simple, but designed to grow into a fuller auth system without re-architecting. It's based on the auth system I built for QuickQuill.

```java
public SessionEntity login(String email, String password) {
  UserEntity user = userRepo.findByEmail(email)
      .orElseThrow(() -> new IllegalArgumentException("Invalid email or password."));
  if (!passwordEncoder.matches(password, user.getPassword()))
    throw new IllegalArgumentException("Invalid email or password.");
  return sessionRepo.save(new SessionEntity(user));
}
```

## Frontend Design

The frontend is a React single-page app (TypeScript + Vite + Tailwind v4) for tracking net worth across bank accounts, investments, credit cards, and loans, with the Plaid integration syncing real bank data. It talks to the Spring Boot backend over a plain REST/JSON API. Visually it's pitch-black — a dark fintech interface styled like a printed currency plate. The design doesn't decorate the finance tracking; it carries it: numbers feel engraved and authoritative because of how they're framed and set in type, which ties the app together from the sign-in screen to the stock pages.

### Design principles

Three rules carry every screen. First, panels aren't rounded cards but flat surfaces framed by an `.engraved` double hairline, so the viewport reads like a stamped document rather than a generic dashboard. Second, serif-for-figures: money values are always set in Libre Caslon while labels and controls use Inter, making balances feel physically printed on the page. Third, micro-detail discipline: 3px corners everywhere, uppercase labels with wide letter-spacing, and tabular numerals so columns align.

### Layout & navigation

One shell — `TabLayout` — defines the layout at every screen size. On desktop, a sticky translucent header holds the brand logo dead center, with Portfolio and Accounts on the left and Stock Market and Profile on the right, over a faint background plate. On mobile, navigation becomes a floating pill-shaped dock pinned to the bottom of the screen, thumb-friendly and safe-area aware. Content sits in a centered column, and the other screens reuse the same plate vocabulary rather than introducing new layout patterns.

### Core components

The component kit is deliberately small — knowing three pieces explains most of the UI. `Card` is the foundational engraved panel that wraps every content section. `StatTile` encodes the figure-display style. `Button` covers four variants (primary, secondary, ghost, danger) tuned to the same aesthetic. The one stand-in for a chart library is `AreaChart`, a hand-rolled SVG with "nice" y-axis ticks, a green gradient fading to transparent, and HTML-rendered labels so they never distort. Responsiveness is a single hook, `useResponsiveLayout`.

## Key Takeaways

- **Put speed where speed lives.** The Monte Carlo engine stays in C++17 and streams results to Spring Boot over OS pipes + JSON rather than being rewritten in Java or wired through JNI. That keeps 10,000+ simulation paths fast and the engine independently buildable and testable with Catch2.
- **Give money a single source of truth.** Plaid's balance is authoritative — imported transactions stay out of `AccountEntity.balance` and live as read-only history records mapped to `DEPOSIT`/`WITHDRAW`. Deriving balances from transaction streams would double-count on every sync and drift from what the bank reports.
- **Defense in depth on secrets.** The `access_token` is encrypted at rest with AES-256-GCM under a derived key, marked `@JsonIgnore` so it's never serialized, and never logged. Also worth it: skipping Plaid's SDK and calling the API directly — the generated client dragged in OkHttp, Retrofit, and Gson for a single integration.
- **Start auth simple, design it to grow.** BCrypt hashing plus UUID token sessions covers the product today, borrowed from QuickQuill, and leaves room for a fuller auth system without re-architecting.
- **Keep the backend boring on purpose.** Controllers, services, and JPA repositories around a plain REST/JSON API — the frontend stays simple because the API stays simple.
- **A tiny design system is a product feature.** One token file, a three-font pairing (serif figures, sans labels), tabular numerals, and a hand-rolled SVG chart mean the engraving-style UI carries the product's identity — and when the kit fits in your head, every new screen looks like it belongs. The constraints are the design.
- **Self-hosting is a stance.** Running the backend on Render and the database on Vercel keeps the ledger your own by default — the tracker never requires surrendering financial data to a third party.
